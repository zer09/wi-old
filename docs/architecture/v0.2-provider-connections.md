# Wi v0.2 provider connections architecture

Status: accepted architecture; Milestone 11 implemented in the current fake/no-network candidate

Date: 2026-07-29

Implementation status: Milestone 11 implements provider-connection identity/catalog, file and environment credentials, explicit routing, capability snapshots, run pinning, lifecycle recovery, and browser management. OpenAI transport, OAuth, live discovery, automatic routing, and later milestones remain unimplemented.

## 1. Purpose and authority

This document freezes the provider-connection architecture for Milestones 11–15. It refines, and does not replace:

- [ADR-0004](../adr/0004-backend-owned-runs.md): runs remain backend-owned;
- [ADR-0005](../adr/0005-direct-provider-adapters.md): OpenAI Platform and ChatGPT/Codex are separate direct adapters and billing identities;
- [ADR-0006](../adr/0006-no-app-server-fallback.md): there is no `codex app-server` fallback;
- [ADR-0007](../adr/0007-partial-stream-policy.md): provider output remains provisional until accepted completion;
- [ADR-0008](../adr/0008-tool-effect-ledger.md): every tool effect remains ledgered;
- [ADR-0012](../adr/0012-trusted-local-user-storage-boundary.md): Wi trusts the local operating-system user.

The released product remains the v0.1 vertical slice. The current Milestone 11 candidate implements the fake/no-network subset identified above; later provider transport, OAuth, discovery, and routing sections remain **planned**.

## 2. Goals and non-goals

The v0.2 provider layer is required to support:

- several simultaneous connections for one provider and authentication mode;
- explicit connection selection for the first implementation;
- immutable run-level provider/account pinning;
- separate OpenAI Platform API-key and ChatGPT/Codex OAuth identities;
- connection-specific capabilities and model discovery;
- a WSL-safe credential store outside `WI_HOME`;
- provider-chain and cache-affinity boundaries;
- provider-neutral state, reasoning, usage, and transport concepts;
- a constrained interface for a possible later automatic router.

Milestone 10 implemented none of this architecture. Milestone 11 now implements the provider-connection, credential, explicit-routing, capability-snapshot, schema/protocol, and management-UI foundations without OAuth, OpenAI requests, live discovery, real tools, or plugins.

## 3. Provider identities and connections

### 3.1 Provider and authentication identities

v0.2 defines two OpenAI provider identities:

```text
openai_platform + api_key
  billing/policy identity: selected OpenAI Platform project/account
  planned first transport: public Responses HTTP/SSE

openai_codex + chatgpt_oauth
  billing/policy identity: selected ChatGPT subject/account/workspace and plan
  planned first transport: ChatGPT/Codex-compatible Responses HTTP/SSE
```

They are separate provider/authentication modes. Wi must never treat them as interchangeable credentials or silently move work between their billing boundaries.

### 3.2 Nonsecret catalog record

Milestone 11 is required to add a runtime-validated catalog record equivalent to:

```ts
interface ProviderConnection {
  connectionId: string;
  providerId: "openai_platform" | "openai_codex";
  authMode: "api_key" | "chatgpt_oauth";

  displayName: string;
  credentialRef: string;
  credentialGeneration: number;

  subjectId?: string;
  accountId?: string;
  workspaceId?: string;
  planType?: string;

  status:
    | "ready"
    | "reauth_required"
    | "disabled"
    | "rate_limited"
    | "unavailable";

  capabilitiesVersion?: string;
  createdAtMs: number;
  updatedAtMs: number;
}
```

Repository conventions may refine names and normalized child records, but these semantics are required. This record is nonsecret. It must not contain an API key, access token, refresh token, authorization code, PKCE verifier, device code, browser credential, or raw authorization header.

`credentialRef` is an opaque backend reference. A file reference must not reveal an arbitrary filesystem path. An environment reference may name the configured environment variable, for example `env:OPENAI_API_KEY`, but never its value.

Provider-connection rows are installation configuration analogous to v0.1 project registration metadata, not canonical session history. No workflow may require an atomic transaction between the catalog, credential backend, and a session database. A run's committed session snapshot remains authoritative for its historical provider identity even if the connection row is later renamed or deleted.

The catalog's session index remains rebuildable from session manifests. Complete catalog loss does not authorize reconstructing active provider connections from historical runs or automatically importing credential files. Credential files are preserved but not automatically rebound; Section 9.4 defines the only explicit recovery path, with bounded backend enumeration, safe candidate metadata, an opaque one-time `recoveryRef`, exact envelope claim, and fail-closed identity conflicts. This matches the existing explicit re-registration rule for lost project metadata without turning credentials into an implicit configuration database.

### 3.3 Stable identity and uniqueness

`connectionId` is Wi's stable selectable identity. Provider-reported identity is used to prevent accidental duplicates when it is authoritative.

For ChatGPT/Codex OAuth, the preferred uniqueness tuple is:

```text
(providerId, authMode, stable subject-or-account identity, workspaceId)
```

Rules:

1. Prefer an issuer-stable `subjectId`; use a stable `accountId` only when the provider contract establishes its meaning.
2. A workspace is part of identity. The same subject/account in two workspaces may have two distinct selectable connections.
3. If a provider has an explicit no-workspace identity, normalize that absence consistently rather than conflating it with an unknown workspace.
4. When authoritative subject/workspace identity is unavailable, Wi must not guess equivalence from display name, email-shaped text, plan name, key prefix, or user-entered alias. Such connections remain distinct by `connectionId` until identity is proven.
5. Platform API keys may represent distinct projects even when their human owner is the same. Wi does not deduplicate them unless authenticated provider metadata supplies a stable project/account identity that the adapter contract declares authoritative.

A completed login for an already-connected subject/workspace binds to the existing `connectionId` rather than creating an accidental copy. Credential replacement is independent of display-name changes. The user may rename an alias without changing provider identity or credential generation.

After authenticated identity is known, identity claim and duplicate resolution occur in one serialized catalog transaction before a completed credential is published. The transaction normalizes an explicit no-workspace value, claims the authoritative uniqueness tuple, and binds the lifecycle operation to either a newly reserved `connectionId` or the already-existing winner. Concurrent attempts for the same tuple therefore return one winning `connectionId`; they cannot commit two connection rows. Any credential update after that claim remains serialized by the winning connection, and one `commandId` can reserve or increment a generation at most once.

### 3.4 Multiple accounts and workspaces

The following must coexist:

```text
OpenAI — Personal ChatGPT Pro
OpenAI — Secondary ChatGPT Pro
OpenAI Platform — Personal Project
OpenAI Platform — Work Project
```

A second ChatGPT login must not overwrite, log out, disable, refresh, or delete the first. One account with two workspaces may be represented as two connection records with independent workspace binding and selection.

Connections have independent:

- credential records and refresh serialization;
- lifecycle status and diagnostics;
- capability snapshots and model availability;
- rate-limit observations;
- provider continuation and cache affinity;
- rename, disable, logout/reauthenticate, and deletion operations.

A refresh for connection A may update only A's credential file and metadata. Disabling, logging out, or deleting A may not mutate B. An active run pinned to A follows the exact credential-lease boundary in Section 4.3; it never moves to B.

### 3.5 Display names

`displayName` is a user-controlled alias, not provider identity. It:

- need not be unique;
- is bounded and treated as untrusted text;
- may be changed without changing `connectionId`;
- must never be used to deduplicate OAuth accounts or Platform projects.

The UI planned for Milestone 11 must show enough nonsecret provider/auth/account/workspace context to distinguish equal aliases.

## 4. Connection lifecycle

### 4.1 States

The planned connection states mean:

| State | Meaning | Selection behavior |
|---|---|---|
| `ready` | Credential reference resolves and the connection is administratively enabled. | Eligible for explicit selection when the requested model/capability is valid. |
| `reauth_required` | OAuth refresh or credential validation requires user authentication. | New runs reject; no fallback. |
| `disabled` | User has disabled the connection without necessarily deleting its credential. | New runs reject; active runs fail explicitly at the next boundary that needs the disabled connection. |
| `rate_limited` | Provider limit metadata says the selected connection cannot currently accept the operation. | Report that connection and reset metadata when safe; no fallback. |
| `unavailable` | Credential backend, environment reference, provider health, or capability state is unavailable/invalid. | New runs reject; no fallback. |

Status is an operational projection, not permission to route. A telemetry update alone cannot select a connection.

### 4.2 Credential generation

`credentialGeneration` binds a run to a credential identity revision.

Increment the generation when:

- an API key is replaced;
- a completed login/relogin replaces the authenticated credential set;
- authenticated subject/account/workspace binding changes;
- another operation changes which principal or billing identity the reference represents.

Ordinary OAuth access-token renewal and provider-mandated refresh-token rotation may update the stored credential **without** incrementing the generation only when the adapter verifies that subject/account/workspace and auth mode are unchanged. Refresh is single-flight per connection. If refreshed identity differs, Wi rejects the refresh result, marks reauthentication required, and must not apply it as the same generation.

An active run may use a same-generation refreshed token for its pinned identity. If the stored generation no longer equals the run snapshot, a later provider step fails with a typed credential-generation error; it never consumes the replacement credential silently.

Relogin A increments only A's generation. It has no effect on B or on a run pinned to B.

### 4.3 Disable, logout, and deletion

These operations are distinct and must be idempotent by `commandId` when exposed to the browser. Every backend-owned command whose acceptance lives in the catalog—including `session.create`, provider lifecycle commands, and provider metadata commands—shares one catalog-global command-ID namespace. Identical method/content reuse returns the original result; reuse by another method or content is a stable conflict regardless of which catalog ledger observed the ID first or whether admissions race.

- **disable**: retain the credential but prohibit new use;
- **logout/disconnect**: delete or revoke that connection's credential as supported and set a non-ready state;
- **delete**: remove that connection's credential independently, then remove/tombstone its catalog metadata according to referential-retention requirements;
- **reauthenticate**: replace the credential for the same proven identity and increment only that connection's generation.

A provider request must acquire a one-request credential lease immediately before it is issued. The lease binds `connectionId`, `credentialGeneration`, and a nonsecret lifecycle revision. Committing disable, or committing the prepared phase of logout/delete/credential replacement, closes issuance of new leases. A request whose lease was acquired before that cutoff may settle under ADR-0007, and a tool call accepted from its valid terminal response may complete through the tool ledger. No later provider request, continuation after a tool result, or token refresh may begin. The next boundary that needs A fails with a typed connection-disabled, credential-unavailable, or generation error and never selects B. A refresh already in flight cannot publish credentials or re-enable the connection after losing the lifecycle-revision compare-and-transition.

Historical run snapshots must remain intelligible after connection deletion. A deletion therefore must not rewrite canonical session events or erase the nonsecret identity snapshot embedded in historical runs. Failure to revoke remotely does not authorize local retention or fallback; report the bounded failure and preserve an honest local state. Remote revocation is not part of the local commit point and an ambiguous non-idempotent remote effect is never retried automatically.

### 4.4 Cross-store lifecycle operations

Catalog metadata and credential files do not share a transaction. Milestone 11 must therefore persist a nonsecret catalog operation for create, credential replace/relogin, logout, and delete. The operation is keyed by `commandId` and canonical-content hash and records only the operation kind, target `connectionId`, expected prior lifecycle revision/generation, reserved target generation or tombstone, opaque credential/provisioning source reference, bounded descriptor identity for an exact claimed stage when present, phase, and safe terminal result. Descriptor identity is device, inode, size, and high-resolution ctime captured by the same no-follow read; the operation never stores credential bytes, credential-derived hashes/fingerprints, OAuth codes, or callback data.

The required ordering and commit points are:

1. Read any provisioning source through a validated no-follow descriptor, obtaining its safe metadata and bounded descriptor identity. In one catalog transaction, reject conflicting `commandId` reuse, acquire the connection's empty lifecycle-operation owner slot, reserve identity/connection/generation as needed, claim that exact provisioning source and descriptor identity once, record phase `prepared`, and close new credential leases for a mutated existing connection. If another command already claimed that provisioning source, persist the losing command as terminal `failed` with `credential.provisioning_already_claimed` in the same transaction; it creates no connection/owner/effect, and identical retry returns that result without rereading a cleaned stage. An identical owner retry returns or resumes the owning operation. A different command cannot prepare while the slot is owned.
2. Reopen the claimed stage through the same validated descriptor path and require exact descriptor identity plus provisioning/provider/auth binding before reading key material. Then perform the one-connection file effect: atomically publish the target envelope for create/replace, or durably remove the exact selected file for logout/delete. Disable is catalog-only and does not use a file effect, but it still acquires the same lifecycle-operation slot under Section 4.5.
3. Observe the bounded file result and, in one catalog transaction, compare the owner identity and expected lifecycle revision, update connection metadata/identity claim, persist phase `succeeded` plus the durable command result, and release the owner slot. A safe pre-effect failure may instead commit phase `failed` and restore prior usability only when the old complete envelope is proven intact.
4. Return/acknowledge the browser or backend-local command only after the terminal catalog transaction commits.

Restart reconciliation is deterministic:

- `prepared` plus the old complete envelope, or target absence plus the complete claimed provisioning/attempt source at its exact recorded descriptor identity, means the local idempotent file effect may be retried;
- `prepared` plus the exact target envelope completes the catalog transition without rewriting or incrementing again;
- a prepared logout/delete plus an absent exact target completes the non-ready/tombstone transition;
- target absence plus a missing claimed source commits one stable typed failure and requires explicit restaging/relogin;
- a terminal operation returns its original safe result for an identical `commandId` retry;
- malformed, mismatched, or unowned files fail the connection closed and are preserved as orphan evidence—never guessed, rebound, or deleted automatically.

Only the recorded owner may reconcile its exact file/reference. Recovery resolves that owner to a terminal result before admitting another lifecycle or credential-mutation operation for the connection. No recovery path requires an atomic catalog/credential/session transaction, and no mismatch authorizes another credential, connection, or generation.

### 4.5 Per-connection lifecycle ownership and precedence

Each connection or reserved connection identity has exactly one durable lifecycle-operation owner slot. The mutually exclusive operations are create publication, API-key replacement, relogin/reauthentication, same-generation OAuth refresh publication, disable, logout/disconnect, delete, and any future administrative enable. Ownership spans catalog prepare through every file effect and terminal catalog commit; serializing only the file write is insufficient.

The slot and revisions have these semantics:

1. A new connection starts at `lifecycleRevision = 1`. Preparing replace, relogin/reauthentication, logout, or delete increments the current lifecycle revision exactly once and records that revision with the owner. This prepare commit is the credential-lease cutoff. Revision values are monotonic, never reused, and remain on a delete tombstone.
2. Disable and any future enable acquire and terminalize the slot in one catalog transaction, incrementing lifecycle revision exactly once. Disable closes new leases; rename never does.
3. A verified same-identity, same-generation token refresh must own the slot while publishing, but does not increment lifecycle revision or generation and cannot change administrative state. It may publish only while owner, revision, generation, and identity all still match.
4. Terminal success or failure releases the slot without another revision increment. Operation history and its stable result remain durable after release.
5. Alias, capability, and rate-limit/health telemetry updates use a separate monotonic metadata revision or disjoint compare-and-set fields. They never own or release the lifecycle slot, increment lifecycle revision/generation, close or open leases, or change a non-ready administrative cutoff. Their updates must merge without overwriting lifecycle-owned fields.

An identical `commandId` and content hash resumes the owner or returns its terminal result. Reuse with different content remains a command conflict. A different lifecycle command received while the slot is owned commits one stable `operation_in_progress` result identifying only the safe owning operation kind; retries of that conflicting command return the same result and it is never queued or executed automatically. The caller must issue a new command after the owner terminates.

A terminal owner compare-and-set cannot lose to a later lifecycle mutation because no later lifecycle mutation can acquire the slot. If owner/revision evidence is nevertheless corrupt or a post-file-effect terminal transition cannot be proven, Wi records `failed_after_effect`, leaves the connection or tombstone explicitly `unavailable`, preserves the exact envelope/deletion and operation evidence, closes leases, and requires explicit recovery. It never restores the prior `ready` state, guesses a generation, or lets the older effect supersede a later cutoff.

Required precedence traces are:

| Interleaving | Frozen outcome |
|---|---|
| Replace owns; disable arrives | Disable receives durable `operation_in_progress`. Replace reconciles first; only a new disable command may then increment the revision and close leases. The completed replace cannot run after that disable. |
| Replace owns; logout arrives | Logout receives durable `operation_in_progress`; replace reaches a terminal result before a newly issued logout may remove the exact credential. |
| Delete owns; reauthenticate arrives | Reauthenticate receives durable `operation_in_progress`; deletion/tombstone reconciliation finishes first and no credential can resurrect the deleted connection. |
| Refresh owns; logout arrives | Logout receives durable `operation_in_progress`; refresh may publish only unchanged-identity same-generation credentials and cannot change administrative state. If logout owns first, refresh cannot start or publish. |
| Replacement C1 owns; distinct replacement C2 arrives | C2 receives its own stable `operation_in_progress`; only C1 owns the one generation reservation and file effect. Retrying C2 never runs it later automatically. |
| Rename/capability/rate telemetry arrives during an owner | The metadata update may commit only through its disjoint metadata revision/fields; it cannot change lifecycle revision, owner, generation, administrative cutoff, or lease availability. |

## 5. Concurrent OAuth attempts

OAuth is deferred to Milestone 13. Its architecture is frozen now.

### 5.1 Attempt identity and secret handling

Each attempt owns independent state equivalent to:

```text
loginId
providerId and authMode
requested display name
OAuth state
PKCE verifier and challenge
creation and expiry time
flow kind: browser_callback or device_code
one-time completion state
provider flow identifiers required by device-code polling
optional selected workspace candidate
```

OAuth state, PKCE verifier, authorization/device codes, and tokens are secret. Wi never writes them to browser-managed storage, catalog SQLite, or session SQLite; a provider-required redirect may transiently transport only the bounded URL parameters governed by Section 5.3. Milestone 13 must persist restart-relevant attempt secrets through a bounded credential-subsystem login-attempt store outside `WI_HOME`, with the same private-root, no-symlink, atomic-write, redaction, and expiry rules as credential files. Attempt records are temporary and separate from the one-file-per-completed-connection credential layout.

The browser receives only safe attempt status and the minimum protocol values required by the chosen OAuth flow. It never receives refresh tokens or the backend PKCE verifier. Wi-generated application/status URLs never contain provider secrets. OAuth protocol parameters are a narrow exception only when the provider requires them in an authorization redirect or callback; Section 5.3 defines their immediate containment and removal.

### 5.2 Attempt state machine

Planned states are equivalent to:

```text
created
awaiting_provider
awaiting_callback
awaiting_device_authorization
awaiting_workspace_selection
completing
completed
denied
cancelled
expired
failed
```

Only one transition from a nonterminal attempt may claim completion. Terminal attempts cannot publish credentials again.

### 5.3 Required behavior

- **Two browser attempts:** each has a unique `loginId`, state value, and PKCE verifier. A callback can complete only the exact matching unexpired attempt.
- **Browser callback:** prefer a provider-supported response mode that keeps authorization codes out of the query. Accept a response only at one dedicated fixed loopback callback path and only with the exact registered method/response mode. The route inherits the existing exact `127.0.0.1` listener and `LoopbackRequestPolicy`: exactly one syntactically valid `Host` matching the active loopback origin/port is mandatory, while missing, duplicate, malformed, forwarded, or nonmatching Host is rejected before callback parsing. Query/form targets are omitted from access logs at every layer; request target, headers, field count/size, total body, content type/charset, and parsing time/depth are bounded, duplicate sensitive fields are rejected, and the raw URL/query/form is never copied or forwarded.
- **Device-code flow:** polling is owned by one attempt, bounded by provider interval/expiry, and survives backend restart only from its external attempt record. A browser connection is not the owner of polling.
- **Denial or cancellation:** terminalize only that attempt, delete its secret attempt material, and create/update no connection credential.
- **Expired code/attempt:** reject completion, mark expired, delete secret attempt material, and require a new attempt.
- **Duplicate callback:** return the original safe terminal result when identity matches; do not exchange twice, increment generation twice, or write a second credential.
- **State mismatch:** reject the callback without consuming or mutating any other attempt. Repeated suspicious mismatches receive bounded diagnostics.
- **Backend restart:** load bounded unexpired attempts from the external attempt store, resume only valid device polling or callback waiting, and expire anything whose safe continuation cannot be proven. No browser tab is required.
- **Account already connected:** after authenticated identity is known, resolve the uniqueness tuple. Replace/relogin the existing matching connection rather than create an accidental duplicate. The result returns the existing `connectionId` and its new generation.
- **Workspace selection:** if one subject can select several workspaces, credential publication pauses in `awaiting_workspace_selection`. Completion binds one explicit workspace. A separate connection requires a separate explicit selection/completion.
- **Refresh-token replacement:** perform a same-directory atomic credential update serialized for that connection. Keep the generation only for a verified unchanged identity; otherwise reject and require reauthentication.

Callback authorization is independent of ordinary browser-session authorization. WebSocket Origin policy is not used for this HTTP route. A top-level provider redirect may have no `Origin` or a cross-site provider `Origin`; either is expected and neither authorizes nor rejects completion. The route sends no CORS permission. A Wi browser cookie is not required, and a present, missing, stale, or unrelated cookie cannot cause acceptance or rejection; callback handling never establishes, rotates, or upgrades a browser credential. Completion authority is the exact unexpired backend attempt identified by `loginId` through one-time state, its backend-held PKCE verifier, the exact registered redirect URI/method/response mode, and the provider response. State is consumed only by the matching transition. After backend restart, the external attempt record—not a browser cookie or Origin—must reconstruct that authority or the attempt expires/fails closed.

A callback response containing or derived from query/form secrets must set `Cache-Control: no-store`, `Pragma: no-cache`, `Referrer-Policy: no-referrer`, and a restrictive no-external-content CSP. It immediately redirects or replaces browser history with a clean same-origin tombstone URL containing no code, state, error description, or provider payload. The tombstone stores only bounded safe terminal status keyed by `loginId`, expires, loads no third-party resources, registers no service worker, and cannot forward a referrer. The tombstone inherits strict Host validation but requires neither Origin nor browser cookie and grants no additional authority. Duplicate callbacks resolve through the backend attempt result, not retained browser parameters. Milestone 13 tests must inspect redirects, history, referrers, storage, service workers, logs, diagnostics, and network requests and prove callback parameters are neither persisted nor forwarded.

OAuth cancellation, callback completion, device polling, refresh, logout, and deletion for connection A must not acquire or mutate connection B's state.

## 6. Explicit selection and run pinning

### 6.1 Active policy

The only active policy planned through Milestone 14 is:

```ts
type ProviderSelectionPolicy = {
  kind: "explicit";
  connectionId: string;
};
```

A session stores a default connection and model for **future** runs. The default is mutable through a durable idempotent command planned for Milestone 11.

### 6.2 Acceptance snapshot

Before acknowledging a run, the backend is required to validate explicit selection and durably snapshot at least:

```text
routing policy and durable selection decision
connectionId
credentialGeneration
credential backend kind and environment backend-process epoch when applicable
providerId
authMode
subject/account/workspace identity
modelId
capabilitiesVersion
promptVersion
toolSchemaHash
reasoning configuration
transport mode
providerChainId
```

The snapshot contains no credential value. Acceptance and the run/provider identity projection occur in the canonical session transaction before acknowledgement or provider work. A routing/selection decision is therefore replayable and auditable.

For an environment-backed connection, acceptance must first resolve a nonempty value within the shared 16,384-byte UTF-8 API-key limit and establish an in-memory credential lease containing a keyed, nonpersisted fingerprint before the run transaction commits. The durable snapshot records only the environment backend and a nonsecret backend-process epoch, never the value or fingerprint. If the transaction fails, the lease is discarded. Every provider request, including the first, re-resolves the variable, re-enforces the same UTF-8 byte limit before hashing or issuance, and must match the accepted lease. Replacement or disappearance after acceptance therefore fails the pinned run before sending another identity's credential. After backend restart the process epoch cannot reproduce the fingerprint, so any accepted nonterminal environment-backed run is interrupted conservatively before provider work and never resumed or rerouted.

Changing the session default from A to B while run A is active does not mutate run A. The next accepted run uses B only after validating B and starts a new provider chain. No provider cursor or opaque state from A crosses to B.

### 6.3 Manual limit behavior

If an explicitly selected connection is rate-limited, unavailable, disabled, or requires reauthentication:

1. report the selected connection and a safe typed status;
2. record provider/rate metadata only as allowed and redacted;
3. do not choose another connection;
4. let the user explicitly select another connection for a later run.

There is no silent retry against another account, workspace, auth mode, provider, endpoint, model, transport, or billing source.

## 7. Provider-chain identity and portability

### 7.1 Provider chain

A `providerChainId` identifies a contiguous provider-affinity lineage. It may span provider steps and, when later continuation is implemented, compatible runs. It is not the Wi session ID or provider response ID.

A new chain is required when any of these changes cannot be proven compatible:

- connection or credential generation;
- provider/auth/account/workspace identity;
- model identity;
- stable prompt/system-instruction version;
- tool schema hash;
- reasoning/opaque-state contract;
- transport continuation contract.

An explicit account/connection switch always starts a new chain and is durably represented. A chain ID never authorizes use of a credential; the run snapshot and current credential checks do.

### 7.2 Portable canonical Wi state

A new chain may rebuild a provider request from bounded canonical Wi state:

```text
visible user/assistant messages
durable tool calls and results
project/session instructions
stable system instructions
compacted canonical summary when a later milestone implements it
context/compaction metadata needed to explain the rebuild
```

Rebuild is normalization, not copying provider-private cursors. Existing partial/interrupted output remains honestly represented under ADR-0007.

### 7.3 Non-portable provider state

The following must not cross a connection change unless a provider contract and a later recorded decision explicitly prove portability:

```text
previous_response_id
connection-local WebSocket continuation
opaque or encrypted reasoning/continuation items
provider response cache identity
account-specific capability state
provider-specific chain cursor
```

Default policy is non-portable. Matching provider/model names do not prove portability. Opaque state is scoped to provider, auth/account/workspace, connection, credential identity, model, and provider chain.

## 8. Cache affinity and telemetry

### 8.1 Affinity key

Cache affinity is scoped to at least:

```text
connectionId
modelId
promptVersion
toolSchemaHash
providerChainId
transportMode
```

Implementations may add provider-declared dimensions. They may not remove `connectionId` or presume previous-response/prompt-cache state is portable across accounts.

Changing an affinity dimension produces a cache miss/new partition unless the adapter explicitly proves a compatible continuation. Canonical full replay remains the correctness path after a cache miss.

### 8.2 Planned telemetry

Milestones 12–15 may collect bounded, redacted observations such as:

```text
input tokens
cached input tokens
cache-write tokens when exposed
latency
active requests
rate-limit and reset metadata
recent failures
model/capability snapshot identity
```

Telemetry must identify its connection/provider/model/chain without containing credentials, raw prompts, hidden reasoning, or arbitrary provider payloads. Telemetry informs a later decision; it does not itself authorize routing, fallback, or billing changes.

## 9. CredentialStore

### 9.1 Interface and explicit backend

The architecture uses the term `CredentialStore`, not `CredentialVault`:

```ts
interface CredentialStore {
  put(ref: string, credential: StoredCredential): Promise<void>;
  get(ref: string): Promise<StoredCredential | null>;
  delete(ref: string): Promise<void>;
  listRefs(): Promise<readonly string[]>;
}
```

Planned backends:

```text
file          default for v0.2
environment   read-only API-key references
keyring       optional later/experimental
```

The first implementation must select a backend explicitly. There is no `auto` backend and no silent fallback between file, environment, and keyring.

### 9.2 Stored credential envelope

The bounded, runtime-validated file payload is equivalent to:

```ts
interface StoredCredentialEnvelope {
  version: 1;
  envelopeId: string;
  connectionId: string;
  providerId: "openai_platform" | "openai_codex";
  authMode: "api_key" | "chatgpt_oauth";
  generation: number;
  updatedAtMs: number;

  identity:
    | { status: "unverified" }
    | {
        status: "authoritative";
        subjectId?: string;
        accountId?: string;
        workspaceId: string | null;
        projectId?: string;
      };

  credential:
    | {
        type: "api_key";
        apiKey: string;
      }
    | {
        type: "chatgpt_oauth";
        accessToken: string;
        refreshToken: string;
        expiresAtMs: number;
        accountId?: string;
        workspaceId?: string;
      };
}
```

`envelopeId` is a backend-generated random nonsecret instance identity changed on each completed replacement; it is not derived from credential bytes. `identity` is the nonsecret identity claim verified when the credential is published. An authoritative claim must contain at least one adapter-declared stable subject/account/project identifier plus normalized workspace presence/absence and must agree with any identity fields in the credential payload. When no authoritative identity exists—such as an unprobed Milestone 11 Platform key—the envelope says `unverified` and uniqueness remains only by `connectionId`; recovery must not invent a claim. Same-identity refresh preserves the authoritative claim, while an authenticated identity change requires a new generation and matching envelope claim. Provider requirements may add bounded fields, issuer/audience metadata, or token-type metadata in a versioned schema. They may not remove envelope versioning/instance identity, connection binding, provider/auth binding, generation, identity-claim semantics, expiry semantics, or bounded secret storage.

A credential file whose envelope identity disagrees with the catalog reference is unavailable; Wi must not repair that mismatch by silently rebinding it.

### 9.3 Backend-only file-credential provisioning

Milestone 11 file-backed API keys enter Wi only through a backend-local `CredentialProvisioner`, not through browser HTTP/WebSocket commands, URLs, command-line arguments, or environment variables. A trusted local CLI or equivalent local administration entrypoint reads bounded secret bytes from masked stdin or a supplied file descriptor and invokes this backend boundary. Concrete command spelling is an implementation choice; the boundary must authenticate the local operating-system user, bound input before retention, and never echo, log, trace, or return the secret.

Before returning success, the provisioner durably writes a versioned staged-secret envelope under `${XDG_STATE_HOME:-$HOME/.local/state}/wi/credential-staging/`, a separate private root that must not overlap `WI_HOME` or the completed credential root. It uses the same Linux-filesystem, `0700` directory, `0600` file, no-symlink, bounded, atomic-write, flush, redaction, and Windows-mount rejection rules as completed credential storage. The envelope contains a generated `provisioningId`, provider/auth binding, bounded creation/expiry times, and the API key. It does not yet claim a `connectionId`. The caller receives only an opaque one-time `provisioningRef`; it is not a path or credential and is treated as a sensitive reference in diagnostics.

The create/replace lifecycle command may carry that nonsecret reference. Its catalog `prepared` transaction claims the `provisioningRef` for exactly one `commandId`, reserves the target connection/generation, and records no secret. A claimed stage does not expire while its operation is nonterminal. The file effect reads the exact claimed stage and publishes the connection-bound final envelope through Section 10.3. Only after the terminal catalog result commits may recovery delete and directory-flush the staged file. Cleanup is idempotent.

Crash outcomes are fixed:

- before the staged envelope commits, no reference is returned and bounded temporary-file cleanup applies;
- after staging but before claim, the unclaimed stage expires and is deleted through bounded startup cleanup;
- after catalog prepare but before final publish, the claimed complete stage survives restart and lets only its owning operation resume;
- after final publish but before terminal catalog commit, recovery verifies that exact final envelope and completes without republishing or incrementing;
- after terminal commit but before stage deletion, recovery removes only that operation's exact stage;
- if both the claimed stage and target final envelope are absent, the operation commits one stable typed failure and requires explicit restaging; it never invents, guesses, or switches a credential.

A `provisioningRef` can be claimed once. Identical retries resume or return the original result; different command/content reuse conflicts. OAuth credentials use the separate Milestone 13 attempt store and then enter the same connection lifecycle after authenticated identity is known.

### 9.4 Explicit recovery after complete catalog loss

Credential recovery is a backend-owned, user-initiated operation, never startup auto-import. It is available only when startup has established a newly rebuilt/replacement catalog and the file `CredentialStore` has surviving managed envelopes. Historical run snapshots and aliases are not candidate-discovery inputs.

The recovery flow is schema-neutral but fixed:

1. **Bounded discovery:** the credential backend enumerates only its generated contained filenames under the validated managed root. It applies the normal no-follow, owner/type/link/mode, size, schema, and envelope checks in cursor pages, but must finish one closed scan epoch over the entire managed root before issuing any eligible reference. Fixed global entry/byte/time limits bound the epoch; exceeding a limit or observing root membership/identity change returns `recovery_scan_incomplete` and issues no `recoveryRef`. Secret bytes and filesystem paths remain inside the credential subsystem.
2. **Safe candidate view:** only after a complete scan proves uniqueness, the backend exposes provider/auth type, original `connectionId`, exact generation, the bounded nonsecret `identity` claim stored in the envelope, update time, and a safe eligibility reason. It issues an expiring opaque one-time `recoveryRef` mapped internally to that exact backend file identity and backend-generated nonsecret `envelopeId`, plus a separate nonclaiming `recoveryEpochId` and expiry time for browser reconciliation. The scanner retains canonical nonsecret metadata plus keyed process-local fingerprints—not complete credential strings—for closure checks. At epoch expiry it clears bindings and safe cached results and zeroes fingerprint/key buffers even if no later request observes the expiry. The reference is bound to the current backend process and scan epoch and intentionally does not survive restart before claim. The epoch ID is safe to persist but can only scope status; it cannot select or claim a candidate. Neither value is a path, credential reference, secret, or user-supplied selector. Duplicate connection or authoritative-identity claims receive only an ineligible safe reason and no claimable reference.
3. **Explicit selection:** the trusted user selects one candidate either through the authenticated local browser administration flow or an equivalent backend-local entrypoint. The command contains `commandId`, canonical-content hash, `recoveryRef`, the displayed expected metadata, and a new bounded display alias if needed; it contains no path or secret. Before send, the browser persists only the safe reconciliation record defined below—including `recoveryEpochId` and expiry, but not the canonical command—and keeps `recoveryRef` and the complete command in memory.
4. **Durable admission:** on command ingress, a bounded per-command admission coordinator synchronously registers `commandId`, recovery operation kind, and `recoveryEpochId` before any asynchronous reference resolution or scan. One catalog transaction then validates command-ID/content-hash reuse and records safe expected metadata plus phase `validating`; it stores no `recoveryRef`, internal credential reference, candidate file identity, or secret and claims/reserves no credential or connection. Status reads serialize with this coordinator: an in-flight pre-commit admission is pending, never final unknown. If the backend restarts in `validating`, the process-bound reference is gone and startup terminalizes that accepted command once as `recovery_ref_expired`.
5. **Exact claim and prepare:** while the in-memory reference remains valid, the admitted owner atomically marks the process-local binding as `claiming` before its first asynchronous rescan; a concurrent caller receives `credential.recovery_already_claimed`, while validation failure releases `claiming` for the admitted owner to retry. The owner completes a new bounded closed scan epoch and revalidates exact file identity, `envelopeId`, metadata, and uniqueness. One catalog transaction compares the `validating` command/hash/epoch, claims the exact backend kind/internal credential reference/`envelopeId` once, reserves an unavailable recovery row under the envelope's original `connectionId` and exact generation, checks any authoritative provider/auth/subject-or-account/project/workspace tuple, initializes lifecycle revision 1 for the rebuilt catalog epoch, acquires the Section 4.5 owner slot, and records phase `prepared`. An `unverified` claim remains distinct only by original `connectionId`; Wi never guesses identity. It never rewrites the envelope to another connection or generation.
6. **Observe and terminalize:** the owner reopens only that generated credential reference, repeats validation, and records `file_observed`. One terminal catalog transaction compares the exact claim and owner, transitions the reserved row to the locally derived `ready`, `reauth_required`, or `unavailable` status, persists the stable safe command result, and releases the slot. Recovery itself performs no provider request and no secret-file rewrite.

Identity and conflict rules are fail closed:

- the original envelope-bound `connectionId` and generation are restored so historical snapshots retain the same identity; display alias may be newly supplied because it is non-identifying;
- a row occupying that `connectionId` with different binding, generation, credential reference, or `envelopeId` yields stable `credential.recovery_connection_conflict`;
- an authoritative provider/auth/subject-or-account-or-project/workspace tuple already claimed by another connection yields stable `credential.recovery_identity_conflict`; Wi does not merge, overwrite, or rebind either connection;
- duplicate files claiming the same original connection or authoritative identity are ambiguous and receive no claimable reference; discovery/claim requires a complete root scan so pagination cannot hide a duplicate;
- malformed, mismatched, unsafe, unowned, already-claimed, or changed envelopes remain preserved and unavailable; they are never chmodded except under Section 10.2, deleted, moved, guessed, or exposed;
- complete catalog loss interrupts nonterminal provider runs before further provider work; recovery preserves historical identity but does not retroactively authorize or resume a pre-loss request.

Retry and crash outcomes are deterministic:

- before durable `validating` admission, the coordinator makes status wait/report pending for an in-flight ingress. If no coordinator/catalog record exists, status remains nonfinal while the referenced recovery epoch can still admit work;
- after `validating` but before `prepared`, no credential claim exists. Backend restart or reference expiry terminalizes the accepted command once as `recovery_ref_expired`; identical retries/status return that result and a fresh bounded scan/new command ID are required;
- after `prepared`, the catalog stores only the backend-internal opaque credential reference, nonsecret `envelopeId`, expected safe metadata, owner state, and bounded descriptor identity (`device`, `inode`, `size`, high-resolution `ctime`) captured by the same no-follow final claim read. It stores no credential-derived hash or fingerprint. Restart reopens through the normal validated descriptor path and requires that exact identity plus envelope binding without the browser reference or a path;
- after `file_observed` but before terminal commit, recovery repeats observation and commits once;
- after terminal commit but before acknowledgement, the reference-free command-status read below returns the original result;
- while the complete command remains in memory, identical `commandId` and content may resume/return the same operation; changed content is a command conflict;
- a different command for a claimed envelope receives stable `credential.recovery_already_claimed`; it never creates another row;
- disappearance, descriptor-identity change, or identity/`envelopeId` change after claim terminalizes the operation as `recovery_source_changed`, including secret-only file replacement across restart. It retains the reserved original connection/generation as an unavailable recovery tombstone, consumes that exact claim permanently, and preserves file/operation evidence;
- an exact claimed candidate cannot be recovered by a new command after terminal failure. The supported next transition is explicit normal staged replacement or reauthentication on the unavailable original-identity tombstone, producing a new envelope/generation under Section 4; Wi does not reinterpret changed evidence as recovery input.

#### Browser lost-ack/reload reconciliation

The browser recovery command is the one planned exception to v0.1's full-canonical-envelope `sessionStorage` journal. Before sending it, the browser durably records a bounded safe reconciliation entry equivalent to:

```text
commandId
operation kind: credential_recovery
nonsecret expected provider/auth/original connection/generation/display metadata
recoveryEpochId and reference expiry time
local phase: unresolved
```

The entry contains no `recoveryRef`, credential/internal reference, `envelopeId`, path, filename, content hash derived from the complete command, or secret. `recoveryEpochId` is a random nonclaiming correlation value unrelated to file identity or credential bytes. The entry is not a command and can never be submitted as one. The complete canonical recovery command and `recoveryRef` remain only in memory while the page is alive.

Milestone 11 must provide a bounded authenticated, non-mutating command-status read keyed by exact `commandId`, expected operation kind, and `recoveryEpochId`. Concrete wire naming is deferred, but its result is fixed:

| Admission/catalog lookup | Safe result and browser action |
|---|---|
| Matching command ingress is registered but its admission transaction is unresolved | `admitting`; keep the safe entry. The status read waits boundedly or reports pending and cannot overtake admission with a final result. |
| No coordinator/catalog record, but the recovery epoch is open or its ingress is not fully drained | `unobserved`; keep the safe entry and retry with bounds. This is not proof of non-acceptance. |
| No coordinator/catalog record after the epoch is closed/expired and every ingress registered to it has settled or been rejected | Repeat the durable lifecycle/metadata command lookup after observing closure and drained ingress. Only if that final lookup is also empty return `not_accepted`; remove the safe entry, perform a fresh complete scan, and use a new `commandId`. The closed epoch makes later admission with its reference impossible, while the final lookup prevents a stale earlier absence from hiding a committed terminal result. |
| Accepted operation is `validating`, `prepared`, or `file_observed` | Return only safe pending phase and bounded display metadata. Keep the safe entry and poll/resubscribe with bounds while backend-owned validation/recovery continues. |
| Operation is terminal | Return the original durable safe success/failure result. Apply it once and remove the safe local entry. |
| `commandId` belongs to another method/epoch or expected safe metadata conflicts | Return a stable typed conflict without exposing either operation. Do not mutate or execute anything. |

The candidate registry closes an epoch at expiry/restart, rejects later commands carrying its references, and drains every synchronously registered admission before status may return `not_accepted`. This coordinator/epoch boundary is the linearization point proving an old command can never later prepare; status itself remains side-effect-free.

The read never accepts command content, claims evidence, starts/resumes recovery, refreshes a reference, changes expiry, or infers an operation from alias, connection metadata, files, provider state, or candidate order. It returns no `recoveryRef`, internal reference, path, filename, envelope identity, or secret. Request/result count, IDs, metadata, bytes, epoch lifetime, admission wait, and polling rate are bounded under existing local browser authentication. Repeated reads are side-effect-free. Secret-free backend status events may reduce polling, but reconnect correctness always uses the read.

The initial server command durably stores its canonical content hash at `validating` admission and applies the normal identical-content/conflicting-content rule. A later same-ID command with different metadata or reference remains a conflict even though the browser persists no hash. Another command cannot claim already-owned evidence. Backend validation/recovery continues independently of browser lifetime after `validating`; restart without the reference converts only that accepted command to stable `recovery_ref_expired`.

The browser clears `recoveryRef` and the complete command from memory on durable acceptance/rejection, expiry, navigation/reload/tab close, or terminalization. If acknowledgement is lost, only the safe reconciliation entry survives reload; after reconnect it obtains the pending/original terminal result by `commandId`, producing no second claim, row, generation, or credential effect.

`recoveryRef`, internal credential references, generated filenames, and paths are redacted from browser URLs, logs, diagnostics, exports, and session/catalog views. The issued `recoveryRef` may appear only in its bounded authenticated candidate response and matching in-memory selection command; it is absent from all unrelated browser payloads, persistent browser storage/history, URLs, logs, diagnostics, traces, fixtures, and exports. Browser/provider input can never manufacture an internal credential reference or path. No hash or fingerprint derived from credential bytes is persisted for recovery. Tests seed distinctive canaries for generated filenames, internal credential references, recovery references, and credential-derived hashes and prove the exact permitted-reference exception and every prohibition.

## 10. WSL/openSUSE file backend

### 10.1 Root and layout

Default root:

```text
${XDG_STATE_HOME:-$HOME/.local/state}/wi/credentials/
```

The default must resolve to the WSL Linux filesystem, not `/mnt/c`. `XDG_STATE_HOME` is accepted only when its canonical root is an absolute path on a filesystem proven to provide the required Linux ownership, exact mode, same-directory atomic rename, file flush, and directory-flush behavior. Validation must reject `/mnt/c`, any canonical `/mnt/<Windows-drive-letter>` path, aliases resolving there, and Windows-backed DrvFS/9p mounts; a lexical absolute-path check is insufficient. If mount identity or required semantics cannot be established safely, configuration fails closed. Configuration must also fail if the canonical credential root overlaps `WI_HOME` in either direction. Credential files are consequently excluded from the documented stopped-`WI_HOME` backup/export boundary.

Managed layout is one file per completed connection:

```text
credentials/
  <backend-generated-opaque-filename>.json
```

The backend derives the filename from validated connection identity. Browser/provider input never supplies a path, filename, temporary name, or credential root.

### 10.2 Modes and containment

Required modes:

```text
credential directory: 0700
credential file:      0600
```

Milestone 11 must:

- create managed directories privately and verify/repair their exact mode;
- canonicalize the configured root once and keep every generated path contained within it;
- reject symlinked managed directories, final credential files, and temporary files;
- reject non-regular files, hard-link ambiguity where detectable, path escape, and identity mismatch;
- never follow an arbitrary credential path from browser, provider, catalog, or session data;
- apply restrictive mode to replacements even when the old file had unsafe mode;
- repair an existing owned final file's unsafe mode before reading any secret bytes.

For existing-file repair, open only the generated contained final path with no-follow semantics, then verify by file descriptor that it is a regular file owned by the Wi operating-system user, has one link, and matches the expected file identity. Only a mode defect on that verified file is repairable: apply `fchmod(0600)`, flush the file and containing directory as supported, then revalidate owner, identity, link count, type, and exact mode on the same descriptor before reading. A symlink, wrong owner, extra hard link, path substitution, failed repair/flush, or identity change is never chmodded or read; that connection fails closed.

These checks are defense in depth under ADR-0012's trusted-same-user boundary. Wi does not claim protection against a hostile same-user process racing every filesystem operation.

### 10.3 Atomic write and crash consistency

Per-connection writes are serialized. A replacement must:

1. validate and bound the complete envelope before filesystem mutation;
2. create an unpredictable same-directory temporary file exclusively with mode `0600`;
3. reject links/non-regular identities;
4. write bounded secret bytes without logging them;
5. flush the file;
6. atomically rename within the credential directory;
7. enforce/repair final mode `0600`;
8. flush the containing directory so the rename is durable where supported;
9. clean safe orphan temporary files through bounded startup recovery.

After a crash, a connection exposes either the old complete envelope or the new complete envelope, never partial JSON. Generation/catalog reconciliation must fail closed on ambiguous mismatch rather than selecting another credential.

Deletion unlinks only the selected connection file and flushes the containing directory. Deleting A never rewrites B. File reads and directory enumeration are bounded by schema, file-size, entry-count, and filename limits established in Milestone 11's operational reference.

### 10.4 Secret boundaries

Credential values must never enter:

- catalog or session SQLite;
- canonical session events or run snapshots;
- browser bootstrap, HTML, storage, or WebSocket payloads;
- logs, diagnostics, traces, test artifacts, or exports;
- `WI_HOME` backup/export.

The file store is plaintext protected by Linux ownership/modes. Wi must not describe it as encrypted. Wi must not add application encryption whose key is stored beside the encrypted file.

The backend must redact authorization material, API keys, access/refresh tokens, OAuth state, PKCE values, device/authorization codes, callback queries, credential values, and sensitive credential references before diagnostics leave the credential subsystem.

### 10.5 Noninteractive restart

The file backend must load valid credentials during a noninteractive openSUSE WSL backend restart without a GUI unlock prompt, D-Bus session, or keyring daemon. A safely repairable mode defect follows Section 10.2 before secret read; unrepairable ownership, identity, permission, schema, containment, generation, or binding defects produce a typed unavailable/reauthentication state and never trigger backend fallback.

## 11. Environment API-key backend

An API-key connection may store a reference such as:

```text
env:OPENAI_API_KEY
```

Rules:

- only the variable name is persisted;
- validate the name against a strict environment-variable-name grammar;
- resolve the value in the backend at each request/use boundary;
- never send the value to the browser or write it to storage/logs;
- OAuth cannot use this read-only backend because token refresh requires persistence;
- a missing or empty value makes that connection `unavailable`;
- a later valid value may restore readiness after explicit/runtime revalidation;
- no missing/changed value triggers file, keyring, another variable, or another connection fallback.

The environment variable's name/reference generation is durable; its secret value can change outside Wi. Run acceptance resolves it before acknowledgement and establishes the Section 6.2 keyed, nonpersisted fingerprint lease. Every request, including the first, must match that accepted fingerprint. Disappearance or replacement after acceptance fails that run explicitly before using another credential, marks the connection unavailable pending explicit/runtime revalidation, and never exposes either value. Wi persists only the backend/process-epoch marker, not the value or fingerprint. Backend restart interrupts an accepted nonterminal environment-backed run because the fingerprint cannot be reconstructed; a later new run re-resolves the explicit connection.

## 13. Capabilities and model discovery

### 13.1 Connection-specific snapshot

Model availability is not a static global list. Each connection has a bounded versioned capability snapshot containing at least:

```text
providerId, authMode, and connectionId
models and stable provider model IDs
reasoning controls and accepted values
reasoning-summary support
tool/function-calling support
transport support
prompt-caching and usage fields
opaque provider-state/continuation support
compaction support when later implemented
retrieval timestamp, source, and capabilitiesVersion
```

The snapshot must not contain credentials. Provider-returned labels are untrusted and bounded.

### 13.2 Discovery and run acceptance

Discovery uses the selected connection's authentication and endpoint. Results for A cannot authorize a run on B. Cached snapshots remain scoped to the connection and have explicit freshness/status metadata.

A run snapshots the exact `capabilitiesVersion` used at acceptance. Later discovery may affect future runs but cannot mutate the active run's accepted model, reasoning controls, transport, or capability contract. If the provider contradicts the accepted snapshot during a run, fail the smallest provider step/run domain and refresh capability state for later selection; do not reroute.

Run acceptance holds a process-local per-connection acceptance lease from the final authoritative selection validation through the session transaction that commits `run.created` and its immutable snapshot. Lifecycle cutoff preparation uses the same per-connection admission boundary and waits for earlier acceptance leases to settle. Snapshot construction performs a final revalidation only after acquiring that lease, so a disable or other cutoff that commits during preliminary capability resolution makes acceptance fail before any user message or run projection is committed. Success and every failure path release the acceptance lease exactly once.

## 14. Provider router boundary

The planned provider-neutral interface is equivalent to:

```ts
interface ProviderRouter {
  select(
    request: ProviderRoutingRequest,
    candidates: readonly ProviderConnectionSnapshot[],
  ): Promise<ProviderRoutingDecision>;
}
```

Milestone 11 implements only `ExplicitProviderRouter`. It validates the requested `connectionId`, capability/model compatibility, status, auth mode, and policy, and produces a durable decision. No automatic candidate ranking or balancing is implemented through Milestone 14.

A future automatic router is permitted only after Milestone 15's telemetry go/no-go decision and a new accepted ADR or explicit amendment. Its minimum constraints are:

- select only before a new run/provider chain;
- never switch connection mid-run;
- never switch after semantic output;
- never switch after a tool effect starts or completes;
- never silently cross ChatGPT-plan and Platform billing;
- keep cross-auth-mode pools disabled unless the user explicitly opts in;
- durably record policy, candidates considered at a bounded level, decision, and fallback reason;
- keep account/workspace/billing identity visible;
- prefer session/provider-chain/cache affinity over naive round-robin;
- make no decision without an explicit routing policy.

## 15. OpenAI state, reasoning, usage, and transport

### 15.1 Provider-neutral concepts

The provider contract is required to represent, without exposing provider secrets:

```text
stable system instructions and promptVersion
model selection
tool schemas and toolSchemaHash
reasoning effort/configuration
provider-approved reasoning summaries
opaque provider continuation items
usage and cached-token accounting
provider response metadata and cursors

```

The core must not parse, request for display, or depend on private hidden chain-of-thought. Provider-approved reasoning summaries are explicit bounded output. Opaque reasoning/continuation state is carried as opaque provider data and never interpreted as tool authorization.

Opaque state may be stored in the canonical session database in Milestone 14 only after schemas define bounds, redaction, browser exclusion, chain binding, and recovery semantics. It is not a credential, but it is sensitive untrusted provider data. It remains scoped to the exact connection/provider/auth/account/workspace/model/chain contract.

### 15.2 Transport order

Implementation order is fixed:

1. Milestone 12: OpenAI Platform Responses HTTP/SSE;
2. Milestone 13: ChatGPT/Codex OAuth adapter on its supported direct Responses surface;
3. Milestone 14: persistent Responses WebSocket optimization and previous-response continuation.

Browser transport remains Wi's multiplexed WebSocket. Provider HTTP/SSE is unrelated to the intentionally absent browser SSE.

A later provider WebSocket failure may recover to HTTP/SSE only within the same explicit connection, account/workspace, auth mode, model, billing identity, and policy. The transport transition is durably represented. It may occur only where ADR-0007 permits retry/verified continuation. After visible semantic output, canonical replay or a provider continuation must prove that output/effects will not duplicate; otherwise interrupt the run. A transport recovery never invokes `codex app-server` and never switches auth mode.

`previous_response_id`, provider chain cursors, and WebSocket continuation are optimizations. Canonical bounded full replay is the correctness path after a cache miss or unavailable continuation.

## 17. Required architecture validations

Later milestones must automate these cases.

### Multiple accounts

- A and B remain logged in simultaneously.
- Concurrent runs use distinct pinned connections.
- Refresh A does not mutate B.
- Disconnect A does not mutate B.
- Relogin A increments only A's generation.
- Simultaneous duplicate logins to A/workspace A atomically resolve to one winning `connectionId`; same subject/different workspace remains distinct.
- Crash/retry at every catalog/file lifecycle boundary returns one stable command result without duplicate generation or cross-connection mutation.
- Replace/disable, replace/logout, delete/reauthenticate, refresh/logout, and distinct-replacement interleavings prove exclusive ownership, monotonic lifecycle revisions, and no credential resurrection.
- Rename/capability/rate telemetry during an owned lifecycle operation changes only disjoint metadata and cannot close/reopen leases or alter the owner.

### OAuth callback route

- Missing, duplicate, malformed, forwarded, non-loopback, and wrong-port Host values are rejected before callback parsing; exact loopback Host succeeds.
- Missing Origin, provider/cross-site Origin, and same-origin Origin neither authorize nor reject a callback and receive no CORS permission.
- Missing, stale, unrelated, and valid Wi browser cookies do not change callback completion, do not establish credentials, and do not affect the tombstone.
- Exact state/PKCE/`loginId`/expiry/redirect method and URI authorize one completion; mismatch, duplicate callback, duplicate fields, oversized/malformed input, and wrong response mode fail deterministically.
- Backend restart resumes only from the external attempt record; callback/tombstone tests retain the no-store/no-referrer/no-external-content/history/network/log guarantees.

### Run pinning

- Session default changes A to B while run A is active.
- A request leased before A's disable/logout cutoff may settle; no new request, refresh, or post-tool continuation starts afterward.
- The next run uses B and a new provider chain.
- No cursor or opaque state crosses to B.

### Manual selection

- Selected A reaches a limit.
- Wi reports A and does not select B.
- The user explicitly selects B only for a later run.

### Credential file

- Backend-only staging survives or safely fails every pre-publish crash boundary and never exposes the staged secret.
- Root is `0700`; files are `0600`; unsafe replacement and safely repairable existing-file modes become `0600` before secret read.
- Symlink and path escape are rejected, including aliases into `/mnt/c` or another Windows-backed mount.
- Replacement is atomic and crash-safe.
- No credential appears in browser, SQLite, URLs generated by Wi, logs, diagnostics, tests, or exports.
- Environment identity is leased before run acknowledgement; replacement before first request fails without using the replacement.
- A stopped `WI_HOME` backup excludes the credential root.
- Noninteractive WSL reload succeeds.
- Complete catalog loss with several surviving envelopes exposes only bounded safe candidate metadata and opaque one-time recovery references; one explicit command restores the exact original connection/generation.
- Recovery rejects original-connection and authoritative-identity conflicts, duplicate/malformed/mismatched envelopes, changed or already-claimed evidence, and arbitrary browser refs/paths without deleting evidence.
- Crash/retry before/after recovery claim, file observation, terminal commit, and acknowledgement produces one stable result and no duplicate connection or claim.
- Prepared or terminal recovery plus lost acknowledgement and page reload retains only the safe reconciliation entry; a bounded command-status read returns pending/original terminal state without another claim or effect.
- Status during pre-admission ingress or pre-prepare validation remains pending; final `not_accepted` requires closed epoch plus drained ingress, then a fresh scan/new command. Conflicting safe metadata fails, and repeated reads remain reference-free and non-mutating.
- Reload/status racing the pre-prepare complete scan cannot discard the safe entry before the command becomes `validating`/terminal, and cannot be followed by a later hidden claim after `not_accepted`.

### Future routing

- No decision exists without a routing policy.
- No mid-run switch is accepted.
- Cross-billing pools require opt-in.
- Affinity contains `connectionId`.
- Fallback after output or a tool effect is rejected.

## 18. Failure policy summary

Provider-connection failures retain the v0.1 smallest-fault-domain policy:

```text
login attempt failure -> fail only that attempt
credential read/update failure -> mark/fail only that connection operation
catalog-loss credential recovery failure -> preserve and fail only that candidate/operation
refresh failure -> reauth_required for that connection
capability failure -> stale/unavailable capability state for that connection
provider request failure -> fail/interupt the pinned provider step/run
router policy failure -> reject run acceptance before provider work
credential subsystem global invariant failure -> fail startup when safe secret handling cannot be guaranteed
```

No failure authorizes another provider, account, workspace, model, endpoint, auth mode, transport, billing source, or `codex app-server`.
